# Minecraft 26.2 API notes

Verified against the decompiled 26.2 sources (Loom 1.17.17, Fabric API 0.156.0+26.2).
Recorded because almost every one of these differs from older Minecraft versions, and
guessing from 1.20/1.21 memory produces code that does not compile — or worse, compiles
and fails at runtime.

## 26.3 delta

Found while porting (Loom 1.18.4, Fabric API 0.163.0+26.3, Gradle 9.7.1). Everything above
still held; this is what additionally changed in 26.3:

- **`Inventory.placeItemBackInInventory(ItemStack)` is gone.** The remaining overloads are
  `placeItemBackInInventory(ItemStack, Prediction)` and
  `placeItemBackInInventory(ItemStack, boolean, Prediction)`. `net.minecraft.util.Prediction`
  is an enum: `PREDICTED` is the client-prediction path, `SERVER_ONLY` is for server-driven
  give-backs — vanilla's `MerchantMenu` passes `SERVER_ONLY`, and so does this mod.
- Loom 1.18 requires Gradle ≥ 9.7 (the wrapper moved from 9.5.1 to 9.7.1 to match).

Fabric no longer publishes Yarn mappings for 26.2 (`meta.fabricmc.net/v2/versions/yarn/26.2`
returns `[]`). The mapping set is Mojang official, so package layout is
`net.minecraft.world.entity...`, and `build.gradle` has no `mappings` line.

## Renames that break ported code

| Older name | 26.2 name |
|---|---|
| `net.minecraft.resources.ResourceLocation` | `net.minecraft.resources.Identifier` (`fromNamespaceAndPath`, `parse`, `withDefaultNamespace` — there is no `Identifier.of`) |
| `net.minecraft.world.entity.npc.Villager` | `net.minecraft.world.entity.npc.villager.Villager` (extra package segment; `AbstractVillager`, `VillagerData`, `VillagerProfession`, `VillagerType`, `VillagerDataHolder` moved too) |
| `EntityType.VILLAGER` / `EntityType.TEXT_DISPLAY` | `EntityTypes.VILLAGER` / `EntityTypes.TEXT_DISPLAY` — the constants moved out of `EntityType` into `net.minecraft.world.entity.EntityTypes` |
| `MobSpawnType` | `net.minecraft.world.entity.EntitySpawnReason` |
| `DimensionDataStorage` | `net.minecraft.world.level.storage.SavedDataStorage` |
| `Level.getDayTime()` | `Level.getOverworldClockTime()` (there is a whole new `net.minecraft.world.clock` package) |
| `Level.isDay()` | `Level.isBrightOutside()` / `isDarkOutside()` |
| `CommandSourceStack.hasPermission(int)` | gone — use `.requires(Commands.hasPermission(Commands.LEVEL_GAMEMASTERS))`, see `net.minecraft.server.permissions` |
| `net.minecraft.world.entity.animal.IronGolem` | `net.minecraft.world.entity.animal.golem.IronGolem` (moved into its own `golem` subpackage) |

## Types that changed shape

- **`InteractionResult` is a sealed interface, not an enum.** Cannot be used in a `switch`
  over enum constants. Constants: `SUCCESS`, `SUCCESS_SERVER`, `CONSUME`, `FAIL`, `PASS`,
  `TRY_WITH_EMPTY_HAND`. Server-side handlers should return `SUCCESS_SERVER` to swallow an
  interaction, `PASS` to let vanilla continue.
- **`ClickEvent` / `HoverEvent` are interfaces with nested records**, not enum+value pairs:
  `new ClickEvent.RunCommand("/cmd")`, `new HoverEvent.ShowText(component)`.
- **`ReputationEventType` is an interface** with anonymous-instance constants and a public
  `register(String)` factory — mods can mint their own. It is not an enum, so no `switch`.
- **`VillagerProfession` is a record** and the static constants are
  `ResourceKey<VillagerProfession>`, not profession instances. `VillagerProfession.name()`
  returns a display `Component`, not a string id — get the id from the `Holder`
  (`holder.unwrapKey()`, `holder.getRegisteredName()`, `holder.is(VillagerProfession.FARMER)`).
- **`VillagerData` is a record of `Holder`s**: `type()`, `profession()`, `level()`, with
  `withType`/`withProfession`/`withLevel` copies.
- **`Display.TextDisplay`** is a public static nested class of
  `net.minecraft.world.entity.Display`. All its setters are `public final` real methods —
  no synched-data poking needed. There is no `setSeeThrough`; see-through is a bit in
  `setFlags(byte)`, constants `Display.TextDisplay.FLAG_SEE_THROUGH` etc.

## Save data: `ValueInput` / `ValueOutput` replaced `CompoundTag`

`net.minecraft.world.level.storage.ValueInput` / `ValueOutput`. Entity hooks are
`protected void addAdditionalSaveData(ValueOutput)` / `readAdditionalSaveData(ValueInput)`.

Gotchas:
- **No UUID accessor at all** — go through `UUIDUtil.CODEC` with `store`/`read`.
- Optional-returning getters exist only for `getInt`, `getLong`, `getString`,
  `getIntArray`, plus `read`/`child`/`childrenList`/`list`. Everything else is
  `getXOr(name, default)`.
- The `MapCodec` overloads and `ValueInput.lookup()` are `@Deprecated`.

## `SavedData` is now codec-driven

`SavedData` itself is just a dirty flag — no `save(CompoundTag)` method. Serialisation
lives in `SavedDataType`:

```java
public record SavedDataType<T extends SavedData>(Identifier id, Supplier<T> constructor, Codec<T> codec, DataFixTypes dataFixType)
```

`DataFixTypes` is a vanilla enum a mod cannot extend — pass an existing constant
(`DataFixTypes.LEVEL` is the least-surprising). Fetch with
`server.getDataStorage().computeIfAbsent(TYPE)` (whole-save scope) or
`level.getDataStorage().computeIfAbsent(TYPE)` (per-dimension). **`setDirty()` on every
mutation is mandatory** or the file is never written.

### `Codec.unboundedMap(UUIDUtil.CODEC, …)` compiles and then fails at runtime

`UUIDUtil.CODEC` encodes to an int-array, which cannot be an NBT compound key. Vanilla's
own pattern for `Map<UUID, V>` (see `GossipContainer`) is a **list of entry records with
the UUID as an ordinary field**, `xmap`ped to/from the map. `UUIDUtil.STRING_CODEC` keys
also work if you want human-readable NBT. This mod uses the list-of-entries pattern.

## Villager internals relevant to this mod

- Brain activities are **no longer registered in `registerBrainGoals`** — that method only
  sets the schedule now. The activity list lives in a `Brain.ActivitySupplier` lambda
  inside the private static `Villager.BRAIN_PROVIDER`, so the old "mixin
  `registerBrainGoals` to add activities" pattern does not work.
- `VillagerMakeLove` is registered in exactly one place:
  `VillagerGoalPackages.getIdlePackage(float)`, under `Activity.IDLE` at priority 3,
  wrapped in a `GateBehavior` keyed on `MemoryModuleType.BREED_TARGET`. The same package
  also sets `BREED_TARGET` via `InteractWith.of(EntityTypes.VILLAGER, …)`.
  Cheapest disable point: `@Inject` into
  `VillagerMakeLove.checkExtraStartConditions(ServerLevel, Villager)` returning `false`.
  `Behavior.tryStart`/`tickOrStop`/`doStop` are `public final` — do not try to override.
- `Villager.foodLevel` has no accessor. `increaseMerchantCareer`, `setUnhappy`,
  `updateSpecialPrices`, `countFoodPointsInInventory` are private — they need
  `@Accessor`/`@Invoker` or an `@Inject`.
- Trade prices key off `getPlayerReputation(Player)` → `gossips.getReputation(uuid, …)`,
  applied in the private `updateSpecialPrices` via `offer.addToSpecialPriceDiff(...)`.
  Hooking gossip therefore moves prices without touching the offer list.
- Villager trades are **data-driven** in 26.2 (`data/minecraft/villager_trade/<profession>/<level>/*.json`).
- **No bell-ring event exists.** Every ring path funnels through
  `BellBlock.attemptToRing(Entity, Level, BlockPos, Direction)` — mixin there. Vanilla also
  sets `MemoryModuleType.HEARD_BELL_TIME` on living entities within 32 blocks.
- Bed POI is `PoiTypes.HOME` (1 ticket); bell POI is `PoiTypes.MEETING`. There is no
  bed-specific tag — filter on the key. Job sites use `PoiTypeTags.ACQUIRABLE_JOB_SITE`.
- Brain memories registered with the one-arg `register(name)` are **runtime-only** and do
  not survive a reload: `WALK_TARGET`, `LOOK_TARGET`, `BREED_TARGET`, `INTERACTION_TARGET`,
  `NEAREST_VISIBLE_PLAYER`, `NEAREST_BED`, `HEARD_BELL_TIME`. `HOME`, `JOB_SITE`,
  `MEETING_POINT` persist. This mod keeps its own state in attachments rather than
  relying on brain memory.

## Fabric API 0.156.0+26.2

- **Data Attachment API** is stable, `net.fabricmc.fabric.api.attachment.v1`. Persistence
  takes a `com.mojang.serialization.Codec`. `AttachmentRegistry.builder()` is deprecated —
  use `AttachmentRegistry.create(Identifier, Consumer<Builder<A>>)`.
  `AttachmentTarget` is injected onto `Entity`, so `villager.getAttachedOrCreate(TYPE)`
  works with no cast.
- `ServerMessageEvents.ALLOW_CHAT_MESSAGE` returning `false` suppresses the broadcast
  entirely **and** skips `CHAT_MESSAGE`. `message.signedContent()` is the raw `String`.
- `ServerEntityEvents.ENTITY_LOAD` is the retrofit hook. A companion interface
  `EntityLoadData` is injected onto `Entity` exposing `spawnReason()` and
  `isLoadedFromDisk()`.
- `ServerPlayerEvents.ALLOW_DEATH` is deprecated; use `ServerLivingEntityEvents.ALLOW_DEATH`.
  For villager deaths use `ServerLivingEntityEvents.AFTER_DEATH` (gives the `DamageSource`,
  hence the killer). `ServerLivingEntityEvents.MOB_CONVERSION` fires on
  villager↔zombie-villager conversion — needed so a cure is not treated as a death.
- `CommandRegistrationCallback.register` takes
  `(CommandDispatcher<CommandSourceStack>, CommandBuildContext, Commands.CommandSelection)`.
  `CommandSourceStack.sendSuccess` takes a `Supplier<Component>`.

## Books, and text entry on a vanilla client

There is no server-side way to open the book **editor**. This rules out asking a player to
type into a book, and it is easy to get wrong because two different methods share one name:

- `ServerPlayer.openItemGui(ItemStack, InteractionHand)` returns immediately unless the stack
  has `DataComponents.WRITTEN_BOOK_CONTENT`. For a signed book it sends
  `ClientboundOpenBookPacket`; for a blank book it does nothing at all.
- `LocalPlayer.openItemGui(...)` — the **client** override — is what constructs
  `BookEditScreen`, reading `DataComponents.WRITABLE_BOOK_CONTENT`. It is reached from
  `WritableBookItem.use`, which the client runs as its own local prediction.
- `ClientPacketListener.handleOpenBook` only ever opens `BookViewScreen`, via
  `BookViewScreen.BookAccess.fromItem(stack)` — read-only.

So the mod uses a plain `minecraft:book` as its input instead: vanilla gives it no
right-click behaviour, so there is no client-side screen to fight and the interaction can be
consumed normally. Text input comes from **chat capture** instead
(`com.talkingvillagers.book.RenamePrompts`), armed by a click event in the book.

**Click events work in books, and that is the mod's only interactive control.**
`BookViewScreen.handleClickEvent` (renamed from `handleComponentClicked`) explicitly handles
only `ClickEvent.ChangePage` and `ClickEvent.RunCommand`, then **falls through to
`Screen.defaultHandleGameClickEvent`** — and that handles the rest, including
`ClickEvent.Custom`. So a book control does not need a command:

- `new ClickEvent.Custom(Identifier id, Optional<Tag> payload)` makes a vanilla client send
  `ServerboundCustomClickActionPacket(id, payload)`. No client mod, nothing in tab-completion,
  and no command string for a player to read off the page and type by hand.
- Vanilla routes it `ServerCommonPacketListenerImpl.handleCustomClickAction` →
  `MinecraftServer.handleCustomClickAction(Identifier, Optional<Tag>)`. The server-level method
  **is not given the player**, so a mod that needs to know who clicked has to hook the listener,
  not the server. `ServerGamePacketListenerImpl.getPlayer()` is public.
- **Inject at `RETURN`, not `HEAD`.** `handleCustomClickAction` opens with
  `PacketUtils.ensureRunningOnSameThread`, which is still on the netty thread and throws to
  reschedule. A `HEAD` inject therefore runs off the server thread. See
  `com.talkingvillagers.mixin.CustomClickActionMixin`.
- The payload is `Optional<Tag>` read through an `UNTRUSTED_TAG_CODEC`. It still arrives from a
  client, so it is a claim, not a fact — re-check the player's standing rather than trusting it.
  Prefer a `StringTag` UUID over `UUIDUtil.CODEC`, which encodes to an int array.

**Book pages overflow invisibly.** There is no truncation and no warning — the client stops
drawing, so content past the bottom of a page is simply gone. Roughly 14 display lines of
~19 characters fit. `com.talkingvillagers.book.Pagination` does this arithmetic and is deliberately
free of Minecraft types so it can be tested standalone.

- Building a signed book: `new WrittenBookContent(Filterable<String> title, String author,
  int generation, List<Filterable<Component>> pages, boolean resolved)`, set as
  `DataComponents.WRITTEN_BOOK_CONTENT` on an `Items.WRITTEN_BOOK` stack.
  `Filterable.passThrough(value)` is the no-filtering wrapper. Title cap is
  `WrittenBookContent.TITLE_MAX_LENGTH`.
- After replacing a held stack, call `player.containerMenu.broadcastChanges()` **before**
  `openItemGui`: the client resolves the open request against the stack it currently believes
  is in that hand, and the inventory sync would otherwise arrive a tick too late.
- Signing a writable book arrives as `ServerboundEditBookPacket(int slot, List<String> pages,
  Optional<String> title)` — title present means signed. `handleEditBook` does **not** call
  `PacketUtils.ensureRunningOnSameThread`, so it runs on the network thread. (Not used by this
  mod any more, but worth knowing if a future feature needs it.)

## Player-facing text without a client mod

- `ServerPlayer.sendSystemMessage(Component, boolean overlay)` — `overlay = true` routes to
  the **action bar**. `Entity.displayClientMessage` does not exist in 26.2.
- Titles: `ClientboundSetTitlesAnimationPacket(fadeIn, stay, fadeOut)`, then
  `ClientboundSetSubtitleTextPacket`, then `ClientboundSetTitleTextPacket`. Send via
  `player.connection.send(...)`.
- **`Entity.getServer()` is gone.** Reach the server through `ServerLevel.getServer()` or a
  tracked reference.
- A custom name shows through walls only when `setCustomNameVisible(true)`. Left false, a
  vanilla client draws it only for the entity under the crosshair — which is limited to the
  player's entity-interaction reach, about three blocks.
